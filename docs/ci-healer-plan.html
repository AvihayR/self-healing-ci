ci‑healer

A production-shaped app whose pipeline reviews its own pull requests, diagnoses its own failures, and proposes its own fixes — under guardrails that assume the agent will cheat.
Two Claude agents live inside GitHub Actions. One reviews every pull request. The other wakes on a red pipeline, reads the wreckage, and opens a fix PR. A human still merges — always. The interesting engineering is not making them work; it is making them safe to trust, because an agent rewarded for a green pipeline will delete your assertions to get one.

Section 01

The thesis

Self-healing is not "an LLM reads the log". It is a control loop with a deliberately adversarial relationship between the thing that proposes fixes and the thing that accepts them.

Most "AI fixes your CI" demos optimise the wrong objective. They reward the agent for turning the build green, and an agent rewarded for green will find the cheapest path to green — which is almost never the correct fix. It is test.skip. It is deleting the assertion that failed. It is continue-on-error: true. The demo looks spectacular and the system it produces is a machine for hiding defects.

This project is built the other way round. The agent proposes; a second, mostly deterministic layer decides whether the proposal is even allowed to be seen by a human. The prompt is not the safety mechanism — the guard is. That inversion is the whole lesson, and it is what makes this worth presenting.

In scope
Diagnosis
Read a failed run, isolate the real error out of thousands of log lines, name the root cause and its class.
In scope
Proposal
A minimal fix on its own branch, verified locally by the agent before it is offered, with the reasoning attached to the PR.
In scope
Review
Every PR — human or agent-authored — gets a second agent's read before a human spends attention on it.
Out of scope
Merging
No agent merges anything, ever. Removing the human is a different project with a different risk profile.

1.1Three loops, not one

The system is easier to reason about as three nested loops with different speeds and different levels of trust.

LoopTriggerActorAuthority
Inner
seconds		Every pushDeterministic CI — lint, types, tests, scansTotal. It is the ground truth everything else argues about.
Middle
~2 min		PR opened or updatedReviewer agentAdvisory. Writes one comment. Cannot block a merge on its own.
Outer
~5 min		CI run concludes failureHealer agent + guardProposal only. Opens a branch and a PR. The guard can veto it before a human ever sees it.

1.2What "done" looks like

The project is finished — as a learning artefact — when you can do this in front of an audience without a script: break the repo from a menu, watch CI go red, watch a PR appear with a correct diagnosis, and then show a second break where the agent tried to cheat and the guard rejected it. Everything in this plan exists to make those four minutes possible and honest.

The uncomfortable design constraint

The healer must be able to edit workflow YAML — that is one of your three chosen failure classes. But it must never edit its own workflow, the reviewer's, or the guard's. The write allowlist is therefore path-based and role-aware, not a blanket "no CI changes" rule. Section 9 specifies it exactly.

Section 02

System architecture

The finished product. Four planes — application, pipeline, cloud, and the lab machinery — meeting inside one repository, with no long-lived credential anywhere in it.

2.1Why the agent layer is a workflow, not a service

Everything Claude does here happens inside an ephemeral GitHub runner that assumes an AWS role for the duration of one job. There is no service to operate, no key to rotate, no inference endpoint to keep alive. The blast radius of a compromised prompt is one job with a scoped GITHUB_TOKEN and a path allowlist — a far easier thing to reason about than a long-lived bot account with standing write access.

2.2Repository layout

# one repo, four planes
apps/api/            Fastify + TypeScript service, Lambda-adapted
apps/web/            React + Vite dashboard; api-types.ts is generated, not hand-written
infra/               Terraform: modules/ + envs/staging + envs/prod + shared/ (the OpenSearch domain)
.github/workflows/   6 callers, 5 reusable (_ prefixed)
.github/actions/     composite actions: setup-workspace, triage-run
.github/agents/      prompts: reviewer.md, healer.md, shared/house-rules.md
breaks/              the catalogue: NN-slug/{patch.diff, expect.json, README.md}
scripts/guard/       green-at-any-cost detector, comment budget, attempt ledger
scripts/scorecard/   drill results → docs/ → Pages
One deliberate asymmetry: the database sits outside Terraform

Neon's free tier gives you a real Postgres with real migrations at no cost. The AWS equivalents would dominate this project's entire running bill for a service handling a hundred requests a day — RDS only while a free tier lasts, Aurora Serverless v2 never. Terraform still owns everything else, so the broken-plan drill is unaffected. If you later want a pure-AWS story for a portfolio, swapping to DynamoDB is one module and one repository class.

Section 03

Canary — the app being protected

A small uptime monitor. Chosen because it fails in interesting ways, demos in one screenshot, and its name is the joke the talk is built on.

You register URLs; a scheduled probe pings them every five minutes; the dashboard shows current status, response-time history and a rolling 30-day availability figure. That is the whole product. It is deliberately small — the app is a substrate for failures, and every hour spent on product features is an hour not spent on the pipeline, which is the actual subject.

Why this app
Time arithmetic
Uptime windows, timezone boundaries, partial buckets. A rich source of subtle logic bugs that a model has to reason about rather than pattern-match.
Why this app
External I/O
The probe makes real HTTP calls. Mock it in tests and you have a first-class flaky-test generator available whenever a drill needs one.
Why this app
A real contract
The UI consumes generated types. Change the API shape without regenerating and the build breaks two directories from the edit — exactly the diagnosis skill being trained.

3.2The API surface

POST   /monitors              register a URL to watch
GET    /monitors              list with current status
GET    /monitors/:id/history  bucketed response times — ?window=24h|7d|30d
                              served by an OpenSearch date_histogram
GET    /monitors/:id/uptime   rolling availability — the function that will host your logic bugs
                              window arithmetic in the API; the counts come from OpenSearch
DELETE /monitors/:id
GET    /healthz               used by the deploy smoke test

One writer per store. The API Lambda reads and writes Postgres — monitors, configuration, users — and only ever reads OpenSearch. Every write to OpenSearch comes from the probe Lambda on the scheduled path. Keeping it to a single writer is what makes the mapping stable, which in turn is what makes a mapper_parsing_exception in a drill mean the catalogue caused it rather than two code paths quietly disagreeing about a field type.

Build the app with tests that deserve trust

The healer's entire safety story rests on "the tests were green afterwards" meaning something. Uptime calculation, bucketing and probe retry logic get real unit tests with real edge cases from day one; everything else can be thin. A lab with weak tests teaches both you and the agent the wrong lesson, and every number on the scorecard inherits that weakness.

3.3What is deliberately not built

No authentication, no multi-tenancy, no pagination, no dark mode. Each is a day of work that adds nothing to the subject. If the project outgrows the lab they are the obvious next tickets — but they are not in this plan, and saying so out loud is what keeps the scope honest.

Notification is the one line that moved. It was on this list, and it comes off — not because it became interesting, but because OpenSearch Alerting does it as configuration. A monitor, a trigger and a destination cost no application code and no evening, so the reason for excluding it no longer holds. Written by hand it would still be out of scope.

Section 04

Infrastructure

Terraform over AWS, two environments, no static credentials — and a second artefact class for the healer to reason about that looks nothing like application code.

4.1Environments

EnvTriggerApprovalPurpose
stagingEvery push to mainNone — automaticWhere deploys actually get exercised. Drills run here; breaking it costs nothing.
prodManual dispatch or a tagGitHub Environment protection rule — you approveExists to make the pipeline honest: an approval gate, a smoke test, and a rollback path you have used at least once on purpose.

Both are separate Terraform root modules under infra/envs/ sharing infra/modules/. Separate roots rather than workspaces — a plan applied against the wrong workspace is a failure mode with no educational value and a real chance of embarrassment mid-demo.

One exception to the duplication: the search domain is shared

Every other resource is duplicated per environment and stays inside free-tier shapes while doing so. The OpenSearch domain does not: two t3.small.search nodes is the difference between a $30 month and a $60 one, for a lab whose prod environment exists to demonstrate an approval gate rather than to serve traffic.

So a single domain lives in a shared root under infra/shared/, and each environment is isolated by index prefix — staging-checks-* and prod-checks-* — with the prefix passed to both Lambdas as configuration. The ISM policy and index template are written once and applied to both patterns.

Name the cost of this honestly. It is weaker isolation than separate roots buy you everywhere else: a misconfigured prefix lets staging write into prod's indices, and no IAM boundary stops it. That is an acceptable trade in a lab and would not be in a real system — and it is worth saying so out loud in the talk, because being able to name the compromise you made is the difference between a shortcut and a decision. It also hands the catalogue a break that could not otherwise exist (break 22).

4.2Identity, and the part that always bites

Actions authenticates to AWS by OIDC federation; no access key exists anywhere in the repo. Three distinct roles, because handing the agent the deploy role would quietly undo the entire guardrail story.

RoleAssumed byPermissions
ci-healer-terraform_terraform.yml on mainFull management of the app's resources plus state bucket. Trust policy pinned to the deploy workflow and branch.
ci-healer-plan-ro_terraform.yml on pull requestsRead-only. Any branch can produce a plan; no branch can apply one.
ci-healer-bedrock_agent.yml onlybedrock:InvokeModel and InvokeModelWithResponseStream on one model ARN. Nothing else — no S3, no Lambda, no IAM.
The two things that will cost you an evening

1. Trust-policy subject matching. The sub claim differs between a branch push (repo:owner/name:ref:refs/heads/main), a pull request (…:pull_request) and an environment-scoped job (…:environment:prod). A role that works on push and fails on PR is almost always this. Match the exact form; resist the bare wildcard.

2. The job needs id-token: write. Missing it does not produce a permissions error — it produces "credentials could not be loaded", which reads like a configuration problem and sends you hunting in entirely the wrong place. Inside a reusable workflow the permission must be granted by the caller: a called workflow can only narrow what it is given, never widen it.

4.3What Terraform manages

Edge and static
Private S3 bucket, CloudFront distribution with origin access control, cache policy, invalidation on each deploy.
Compute
Two Lambdas (API and probe) on arm64, an HTTP API Gateway, log groups with 14-day retention so the free tier stays free.
Schedule and config
EventBridge Scheduler rule driving the probe; SSM parameters for runtime config and the Neon connection string.
Search — shared root
One aws_opensearch_domain for both environments, single t3.small.search node, EBS-backed, fine-grained access control on. Lives in infra/shared/, not per-env. Index template and ISM policy applied as Terraform-managed documents against both prefixes. Each environment's Lambda execution roles get es:ESHttp* scoped to the domain ARN — read-only for the API, write for the probe — and the index prefix arrives as configuration, not as an IAM boundary.
State and identity
Versioned S3 state bucket with native locking; the three IAM roles and the GitHub OIDC provider itself.

4.4Deploy sequence

plan    terraform plan -out=tfplan       → summary posted as ONE sticky PR comment
gate    environment approval             prod only
apply   terraform apply tfplan           → the exact plan reviewed; never a re-plan
ship    lambda publish + alias shift · s3 sync --delete · cloudfront invalidate
verify  smoke: GET /healthz + one probe round-trip
        non-200 → automatic alias rollback, job fails, healer stays out of it

Apply consumes the saved plan file rather than re-planning, so what was approved is what runs — the same discipline the healer's proposals are held to. Deploy failures deliberately do not wake the healer: a bad deploy wants a rollback and a human, not a fix PR.

Section 05

Pipeline topology

Six caller workflows, five reusable ones, two composite actions. The split is not cosmetic — it is what stops the healer from being able to edit the thing that judges it.

5.1Reusable workflow or composite action?

They solve different problems and mixing them up produces a repo that is technically DRY and practically unmaintainable. The rule used here:

Reusable workflow (workflow_call)Composite action
UnitOne or more whole jobs, each on its own runnerA sequence of steps inside someone else's job
Use whenThe thing needs its own runner, its own permissions, or its own matrixThe thing is glue repeated at the top of many jobs
SecretsDeclared explicitly, or secrets: inheritPassed as inputs — no implicit access
HereCI, security, agent, terraform, deploysetup-workspace, triage-run
Reusable-workflow rules worth knowing before you hit them
  • Permissions can only narrow. A called workflow never gains a permission its caller lacked. If the healer needs pull-requests: write, the caller must grant it — which is exactly the audit trail you want.
  • Nesting is capped at four levels, and one caller may reference at most twenty reusable workflows. This design uses two levels, so it never comes close.
  • env: does not propagate from caller to called workflow. Repository and organisation vars do. Pass anything else as an explicit input — the explicitness is a feature here, since the input list becomes the agent's policy surface.
  • A workflow_run caller always executes the definition on the default branch, whatever the failed run's branch was. That single fact is why approach A was chosen: a pull request cannot modify the healer that judges it.

5.2The CI caller

name: CI
on: { push: { branches: [main] }, pull_request: {} }
permissions: { contents: read }

jobs:
  verify:
    uses: ./.github/workflows/_node-ci.yml
    with: { node-version: '22', coverage-floor: 70 }
  security:
    uses: ./.github/workflows/_security.yml
    permissions: { contents: read, pull-requests: read }
  # fan-out is intentional: a lint failure and a test failure must be
  # distinguishable jobs, or the healer's triage has nothing to grip.

Granularity here is a design decision, not a style choice. Every job you merge together is a distinction the classifier can no longer make. _node-ci.yml therefore exposes lint, typecheck, test, contracts and build as separate jobs sharing one setup-workspace composite.

Section 06

The agent platform

One reusable workflow is the only place in the repository allowed to talk to a model. Both agents are the same runner with different policy.

Centralising this matters more than it first appears. Cost caps, redaction, tool allowlists, timeout, model choice and audit logging are written once and cannot be bypassed by adding a new workflow — because there is no second path to Bedrock. When you later tighten a rule, both agents tighten together.

6.1Interface

on:
  workflow_call:
    inputs:
      role:          { type: string,  required: true }   # reviewer | healer
      prompt:        { type: string,  required: true }   # path under .github/agents/
      context-artifact: { type: string, required: false } # triage output to mount
      write-scope:   { type: string,  default: '' }      # newline-separated path globs
      allowed-tools: { type: string,  required: true }
      max-turns:     { type: number,  default: 24 }
      usd-ceiling:   { type: number,  default: 1.50 }
      model:         { type: string,  required: true }
    outputs:
      verdict:  { description: 'pass | findings | fix-proposed | gave-up' }
      summary:  { description: 'path to the agent-authored markdown summary' }
      usd-spent: {}

6.2Auth path

The job requests id-token: write, assumes ci-healer-bedrock, and runs the Claude Code action in Bedrock mode. Model selection is by Bedrock inference-profile identifier for your region — look it up in the Bedrock console exactly as you did for the celebration pipeline; do not hand-assemble the string, and do not assume a model available in us-east-1 is available in yours.

steps:
  - uses: aws-actions/configure-aws-credentials@<pinned-sha>
    with: { role-to-assume: ${{ secrets.AWS_BEDROCK_ROLE }}, aws-region: ${{ vars.AWS_REGION }} }
  - uses: anthropics/claude-code-action@<pinned-sha>
    env:
      CLAUDE_CODE_USE_BEDROCK: '1'
      AWS_REGION: ${{ vars.AWS_REGION }}
      ANTHROPIC_MODEL: ${{ inputs.model }}     # regional inference profile id
Pin every third-party action by commit SHA

You already do this in the Trello repo and it matters more here: two of these actions run with a token that can write to pull requests. A moving tag is a supply-chain hole, and "the agent's action got hijacked" is a much worse story than any bug the agent could introduce.

6.3Model selection

JobModelWhy
Reviewerclaude-opus-5Review quality is the product. A cheaper model produces findings you learn to ignore, and an ignored reviewer is worse than none.
Healerclaude-opus-5Root-cause reasoning across logs, diff and source is the hardest task in the system.
Log summarisationclaude-haiku-4-5Optional. Only if deterministic triage leaves an oversized log; a cheap model compressing text is a good fit, and it is on the same Bedrock role.
Classification— none —Deterministic regex signatures. Never spend a model call on something grep answers correctly every time.

Both agent roles start at the same model deliberately: when you later measure whether a smaller model reviews as well, you want a clean baseline to compare against, and the scorecard in section 11 is exactly the instrument for that experiment.

6.4House rules — shared by both agents

One prompt file, .github/agents/shared/house-rules.md, is prepended to both roles. It encodes the output discipline you asked for, and it is deliberately short — long prompts drift.

RuleStatement given to the agent
One artefactProduce exactly one durable output — one comment, or one pull request. Never post progress updates, never open a second comment, never announce what you are about to do.
Code comments: one lineComment a changed line only when the reason is not evident from the code. One line, directly above the change, explaining why — not what. Go beyond one line only for a genuine workaround, an external quirk, or a non-obvious invariant, and then only as many lines as the reason needs.
No signaturesNever add "fixed by AI", banner comments, decorative separators, emoji, or TODOs. Nothing in the diff should announce its author.
No restatingNever write a comment that paraphrases the line under it. If a reader could derive it in two seconds, delete it.
Minimal diffChange the fewest lines that fix the stated root cause. Unrelated improvements, reformatting and renames are out of scope even when tempting.
Say when unsureIf the evidence does not support a confident root cause, say so and stop. A well-argued "I could not determine this" is a success; a plausible guess presented as fact is a failure.

Enforced, not merely requested

scripts/guard/comment-budget.mjs runs on every agent-authored PR and fails it when the diff adds a comment block longer than four lines without a matching justification line in the PR body, when added comment lines exceed 40% of added code lines, or when it finds a signature, banner or new TODO. Prompt rules drift under pressure; a check does not.

Section 07

The PR reviewer

Runs on every pull request and again on every push to it. One comment, edited in place, for the entire life of the PR.

7.1Trigger and re-run behaviour

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review]
concurrency:
  group: review-${{ github.event.pull_request.number }}
  cancel-in-progress: true     # a fast follow-up push supersedes the in-flight review
permissions: { contents: read, pull-requests: write }
jobs:
  review:
    if: github.event.pull_request.draft == false
    uses: ./.github/workflows/_agent.yml
    with: { role: reviewer, prompt: .github/agents/reviewer.md, write-scope: '' }
    secrets: inherit

synchronize is what satisfies "runs again on fixes": every push to the branch re-reviews it. cancel-in-progress means three pushes in a minute cost one review, not three. The empty write-scope is the reviewer's cage — it has no write access to the working tree at all, so a prompt injection in a PR's own source cannot turn it into an editor.

7.2The single sticky comment

The reviewer's first act is to search the PR for a comment containing the marker <!-- ci-healer:review -->. If one exists it is edited; otherwise one is created. There is never a second. The comment always reflects the current head commit, so scrolling back through review archaeology is impossible by construction.

Section of the commentContents
Verdict lineOne of looks good comments blocking concern, plus the head SHA it applies to.
BlockersAt most three. Each cites file:line and states the failure it would cause — not a style opinion.
Worth consideringAt most four. Real improvements the author may reasonably decline.
NitsCollapsed <details> block, capped at five, never repeated after the author has pushed past them.
Nothing elseNo summary of the diff, no praise paragraph, no restatement of the PR description. The author wrote it; they know what it says.

7.3Inline comments — deliberately rationed

Inline review comments are allowed only for blockers, capped at three, and only where the exact line matters. Everything else lives in the sticky comment. This is the anti-spam rule with teeth: a reviewer that leaves fourteen inline nitpicks trains you to collapse its output, and a reviewer nobody reads is dead weight in the pipeline.

7.4Reviewing the healer

The reviewer treats healer-authored pull requests exactly like human ones, with two extra questions in its prompt: does the stated root cause actually explain the observed failure? and does this diff make the symptom disappear without addressing the cause? This is the second pair of eyes on the machine, and it is the most quietly interesting property of the system — one agent's output is another agent's input, with a deterministic guard sitting between them and a human at the end.

Why the reviewer cannot block a merge

It posts a comment; it is not a required status check. An advisory reviewer that is sometimes wrong is a useful colleague. A blocking reviewer that is sometimes wrong is an outage, and the first time it wrongly blocks a merge at 2am you will disable it permanently — losing the good it does along with the bad.

Section 08

The self-healing pipeline

Eleven stages from red build to reviewable pull request. Only one of them contains a model — and it is the last place the design reaches for, not the first.

8.1Stage notes

StageWhat it actually does, and why it is separate
2 EligibilityRefuses to run when the failed branch already starts with heal/ (no healing the healer), when the failure fingerprint has two attempts in 24 hours, when the run is older than an hour, or when the PR came from a fork. Cheap, deterministic, and the difference between a lab and a runaway.
3 CollectDownloads the run's log archive through the API, plus the machine-readable test report uploaded by the failing job. The test report matters: a JUnit/JSON report names the failing test and its assertion directly, where a log requires inference.
4 TriageStrips ANSI, finds the failing step, keeps the error block and a tail window, and redacts anything matching a secret shape. Hard cap of 400 lines. Feeding a whole log to a model is expensive, slower, and less accurate — the signal drowns.
5 ClassifyRegex signatures produce a class and a confidence. Two jobs: route the failure, and provide the ground-truth label the scorecard grades the agent's own classification against.
6 HealThe agent gets the classified evidence, the diff, and write access limited to the paths its class permits. It must reproduce the failure locally before proposing anything.
7 Self-verifyThe fix is proven by re-running the failing job in the same runner. An unverified fix is never proposed — "I think this works" is not a pull request.
8 GuardSection 9. The deterministic veto, and the most important code in the repository.
9 ProposeOne branch heal/<fingerprint>, one PR, labelled heal:proposed plus its class, linking the failed run. Zero comments on any other PR.

Section 09

Guardrails — assuming the agent cheats

Not because the model is malicious, but because "make CI pass" and "make the code correct" are different objectives, and only one of them is observable from inside a job.

9.1The green-at-any-cost detector

Runs on the healer's diff before any PR exists. Any single trip rejects the whole proposal: the branch is deleted, the attempt is logged as a false heal, and no pull request is opened. There is no override flag — a rejected heal is a data point, not an obstacle.

CheckRejectsRationale
Assertion countFewer assertions or test cases after the fix than beforeThe single most common cheat. Compare parsed counts between base and head, per file.
Skip markersAdded .skip, .only, xit, todo:, --passWithNoTestsSilencing a test is not fixing it. Quarantine is a separate, explicit proposal type with its own label.
Gate weakeningAdded continue-on-error, || true, or a removed gating stepTurning off the alarm rather than putting out the fire.
SuppressionsNew @ts-ignore, @ts-expect-error, eslint-disable, loosened tsconfig or rule configType and lint errors are the failure, not the messenger.
Test-file editsAny change under a test path when the class is not test-failure or flakeThe class must justify the paths touched. A dependency fix has no business editing a test.
CoverageLine coverage down more than one pointCatches deletion-shaped fixes the assertion counter misses.
Self-modificationAny edit to heal.yml, pr-review.yml, _agent.yml, scripts/guard/**, breaks/**Absolute. The agent may fix workflows; never the ones that constrain or grade it.
Blast radiusMore than 3 files or 120 changed linesA correct root-cause fix is small. A large diff means the agent is guessing, and it should say so instead.
Test this guard the way you would test authentication

Write unit tests that feed it known-cheating diffs — a deleted assertion, an added .skip, a loosened lint rule — and assert that each is rejected. This is the one component whose failure is silent: a broken guard does not error, it simply starts approving everything, and you will not notice for weeks.

9.3Loop breaking and cost

Fingerprint ledger
SHA of workflow + job + failing step + normalised first error. Two attempts per fingerprint per 24h, stored as JSON on an orphan healer-state branch. Third failure files an issue and stops.
No self-triggering
The healer ignores any run whose head branch matches heal/*. Without this, one bad fix becomes an infinite loop of increasingly creative bad fixes.
Hard ceilings
Per-run: max-turns, a USD ceiling and a 15-minute job timeout. Per-day: a repository-level cap after which the healer no-ops and says so in the run summary.
Fork safety
workflow_run carries write permissions even for fork PRs. The healer therefore refuses fork-originated runs outright — it never checks out untrusted code with a writable token.

9.4Secret hygiene

The redaction pass in triage runs before anything reaches the model: anything shaped like a token, key, bearer header, connection string or E.164 phone number is replaced with a typed placeholder such as <redacted:aws-key>. The placeholder matters — the agent must be able to reason that a credential was present without ever seeing it. Config-class failures are diagnosed from symptom and shape alone, which is exactly the constraint a human on-caller works under when they lack production access.

Section 10

The break catalogue

Twenty-two deliberate failures. This is the curriculum — the thing that turns "I built an AI workflow" into "I drilled it ninety times and here is what it gets wrong".

Each break is a directory under breaks/ holding a patch, a README explaining the intended lesson, and an expect.json declaring what a correct outcome looks like. The drill workflow applies the patch on a fresh branch, opens a PR, and lets the machinery run untouched. Because the expectation is declared up front, grading is automatic and honest — you cannot rationalise a wrong answer after seeing it.

Breaks 04, 09, 13 and 19 are the ones worth demonstrating

Each has a cheap wrong answer that turns the pipeline green. They are where the guard earns its place, where the scorecard's false-heal number comes from, and where a talk stops being a demo and starts being an argument. Build them early — before the healer is polished — so you are tuning against the hard cases rather than the easy ones. Break 19 is the sharpest of the four, because its wrong answer is not a green pipeline hiding a red one — it is a green pipeline hiding a wrong number, with nothing failing anywhere to give it away.

11.2The four numbers that matter

Primary
False-heal rate
Fixes that went green and were wrong — caught by the guard, the reviewer, or you. Every other metric can be gamed by trying harder; this one only improves when the system gets safer. Target: falling, and never hidden.
Primary
Correct-heal rate
Merged unchanged, by a human who read it. Not "PR opened" — opening a PR is not an achievement.
Secondary
Cost per correct heal
Total agent spend ÷ correct heals. Rises sharply when the agent flails, which makes it an early warning that a prompt change made things worse.
Secondary
Reviewer agreement
How often the reviewer's verdict matched yours. Below about 70% the reviewer is noise and needs its prompt cut back, not extended.

11.3The dashboard

A static page built by scripts/scorecard/ and published to GitHub Pages: the four headline numbers, a per-break grid showing which drills the system reliably passes and which it still fails, and a timeline of runs annotated with prompt-version changes so you can see which edit moved which number. It is a single HTML file with no dependencies — and it is the link that goes in the README, the CV bullet and the last slide.

Version the prompts like code, because they are

Every record stores the SHA of the prompt files used. Without that, a scorecard is a pile of numbers from different systems, and the one question you actually want to answer — "did that prompt change help?" — becomes unanswerable after the third edit.

The talk

Built into the plan rather than bolted on afterwards, because a project you can explain in four minutes is worth more than one you can only demonstrate.

14.1Five beats

BeatWhat you say and show
1The hook"Every self-healing CI demo you have seen optimises for a green build. Here is why that is the wrong objective — and what it looks like when you optimise for a correct one instead." Thirty seconds, no slides.
2The systemFigure 1, ten seconds per plane. The line that lands: one agent proposes, one agent reviews, and the thing that decides whether either is allowed to speak is ordinary deterministic code.
3The live drillInject break 01 from the drill menu. CI goes red. Talk over the ninety seconds of waiting — this is where you explain triage, because the audience is watching a progress bar anyway. A PR appears with a correct root cause.

14.2Rehearsal notes

  • Pre-warm everything. A cold npm ci and a cold Lambda turn ninety seconds of dead air into four minutes. Run one throwaway drill immediately before you present.
  • Have a recording of beat 4. The one demo that must not fail live is the one where the guard fires. Show the recording if the live run stalls; nobody minds, and the point survives intact.
  • Do not explain the app. Twenty words: "it pings URLs and shows uptime". Every extra sentence about Canary is a sentence not spent on the pipeline.
  • Know your own numbers cold. The first question will be "how often is it wrong?". Answering with a real figure, unprompted, is worth more than the entire demo.
